### S019 · NOMAD user guide (Technical report G-2009-37, Les cahiers du GERAD 2009, no DOI/arXiv; text read: Version 3.7.2, revised August 2015)
**Role**: core · **Coauthors**: S. Le Digabel, C. Tribes. The title page of the revision orders them Le Digabel, Tribes, Audet (p. 3). The guide's own self-citation [25] orders them Audet, Le Digabel, Tribes (p. 115). · **Position in trajectory**: This is the user reference for NOMAD 3.x. The companion software paper is Le Digabel's TOMS Algorithm 909 (2011), cited as [51] together with [25] (p. 4, p. 5). The guide itself separates who designed the methods (Abramson, Audet, Dennis, Le Digabel, Tribes) from who wrote the code: Couture before 3.0, Le Digabel from 3.0, Tribes from 3.5.1 (p. 20). Development started in 2001 (p. 19). The guide predates the NOMAD 4 redesign (TOMS 2022; this date comes from SKILL.md, not from the guide). **Read**: the whole text, pp. 1–121. The installation chapter (pp. 23–33), the index (pp. 119–121) and the C++ code listings were skimmed. The bibliography (pp. 113–118) was read and checked against the in-text citations.

- **D1 Problem & entry**: The guide enters from the user's problem class, not from an algorithm. The preface defines the target by the pathologies of real simulators (p. 11):
  - some constraints can be evaluated before the simulation is launched, others only afterwards;
  - one simulation takes "several seconds, minutes hours or even days";
  - outputs have limited precision and numerical noise;
  - the blackbox may fail even when the input looks acceptable;
  - two runs from the same input may give different outputs;
  - derivatives are "unknown, hidden, unreliable or inexistent".

  The preface then scopes the tool *negatively*: it is not the right tool for convex problems, for smooth functions that are cheap to evaluate, or for many variables. It is intended for time-consuming blackboxes with few variables and is "often useful when other optimizers fail" (p. 11). §1.1 repeats the three defining traits: no exploitable derivatives, noise, and failure even at feasible points (p. 15). The formal statement is min_{x∈Ω} f(x) with Ω = {x ∈ X : c_j(x) ≤ 0, j ∈ J} and f, c_j : X → ℝ ∪ {∞} (eq. 1.1, p. 16; eq. 3.1, p. 37). Failure is written into the codomain of the problem.
  - Transferable technique: open a method or software paper with (a) a list of the pathologies your method is built for and (b) one sentence naming the problem classes where the reader should use something else (p. 11).
  - Transferable technique: write failure into the problem statement (f : X → ℝ ∪ {∞}) so that crashes are part of the model rather than an implementation detail (p. 16).
- **D2 Core idea & algorithm design**: The skeleton is the high-level MADS loop (Algorithm 1, p. 17): search on the mesh; if the search fails, poll on the mesh; on success, coarsen the mesh; on failure, keep x_k and refine it. The guide states the division of labour: the search is flexible and therefore "a difficulty for the theory", while the poll is "more rigidly defined" and "the basis of the convergence analysis" (pp. 16–17). Almost every feature of NOMAD 3.7.2 hangs on one of four slots of this skeleton:
  1. **Search slot.** It holds the default quadratic-model search, which proposes up to 4 trial points per iteration, projected to the mesh by default (p. 99, p. 105, p. 110). It also holds the Latin-hypercube search (p. 58), the VNS search, "coded as a NOMAD::Search sub-class" (p. 99), the speculative search (p. 81), the cache search (p. 80, p. 96), TGP statistical models (pp. 111–112) and a user search (pp. 99–100).
  2. **Poll slot.** Sixteen direction types are available (GPS, LT-MADS, OrthoMADS, with 1, 2, n+1 or 2n directions) (pp. 54–55). The default is ORTHO N+1 QUAD, in which a quadratic model chooses the (n+1)-th poll direction (p. 55, p. 83). The poll size is set per variable, and the anisotropic XMesh adapts it to the direction of success (p. 57, p. 80, p. 104). Each variable group gets its own poll directions (p. 85, p. 107). Categorical variables are handled by an extended poll over neighbours supplied by the user (pp. 87–89).
  3. **Constraint slot.** Constraints are handled by EB, PB, PEB or filter F (p. 53), with progressive-barrier knobs H_MAX_0, H_MIN, H_NORM and RHO (pp. 80–81). The logs show a "PhaseOne" stage when x0 violates the EB constraint (p. 45; x0 gives c2 = 20 > 0, p. 39). The text never explains PhaseOne; it appears only in the logs and in a release-note bug fix (p. 105).
  4. **Evaluation-management slot.** It covers the opportunistic strategy (p. 84), the cache (p. 50, p. 58), evaluation of blocks of points (pp. 91–92), the CNT_EVAL output and count_eval flag (p. 53, p. 64), and surrogate ordering of trial points (p. 79).

  What stays fixed: trial points lie on the mesh (p. 100), and the poll directions carry convergence, even in the parallel space-decomposition variant, where a "pollster" working on all variables "ensures the convergence of the algorithm" (p. 97). A second design move is **composition by MADS runs**. BiMADS is a series of single-objective MADS runs (p. 90). VNS runs MADS from perturbed points (p. 99). A categorical extended poll launches a MADS "extended poll descent" (p. 88). Coop-MADS runs several MADS instances with different seeds around one cache server (p. 96). PSD-MADS runs MADS on randomly chosen subsets of ns variables, with ns = 2 in [21] and [52] (p. 97). Multistart runs MADS from LH points (p. 68). The detailed sensitivity tool calls BiMADS (p. 98).
  - Transferable technique: expose each acceleration as a separately switchable component, and ship a single switch that removes all model use (DISABLE MODELS, p. 83). Anyone can then ablate the models against the bare algorithm.
  - Transferable technique: build a new algorithm (multiobjective, global, mixed-variable, parallel) as a driver that calls the convergent base method as a subroutine. The base method's guarantee then comes along for free (pp. 88, 90, 96–99).
- **D3 Assumptions & model**: The guide states no smoothness assumption. The theory is delegated to [18], [8] and [20] (p. 15, p. 16). The user-facing assumptions are practical:
  - *few variables.* NOMAD is "in general efficient" up to about 20 variables (the comparison symbol is garbled in the text), and PSD-MADS has solved up to 500 (p. 97). DIMENSION is capped at 1000, but the comparison symbol is lost in extraction (p. 49).
  - *expensive evaluations* (p. 11).
  - *the user classifies the constraints.* EB constraints "need to be always satisfied (unrelaxable constraints)". PB, PEB and F constraints need to hold only at the solution. Hidden constraints show up only as failed evaluations. If the user is unsure, CSTR (that is, PB) is suggested (p. 53).
  - *bounds are declared to NOMAD, not coded in the blackbox* (p. 41). Scaling comes from the bounds, or from the SCALING parameter when there are none (p. 84).
  - *surrogates are static and supplied by the user* (p. 84). TGP models are the dynamic exception (p. 111).

  The guide names noise (p. 11), but I found no parameter for replications or noise handling in any parameter table (pp. 49–50, 79–82, 110). Assumptions the guide admits are there for the theory or the implementation: search points must lie on the current mesh (p. 100); batch-mode categorical neighbours must keep the number of variables (p. 88); categorical problems need explicit starting points, because an LH search has no signature to sample from (p. 89).
  - Transferable technique: give each blackbox output exactly one declared semantic type in the problem file (OBJ, EB, PB, PEB, F, CNT_EVAL, STAT_SUM, …) so that the constraint treatment is a modelling decision rather than code (p. 53).
- **D4 Analysis & proof**: Not applicable. The guide contains no theorem, lemma or proof. Theory appears only as invariants that the user must respect when extending the code:
  - "the MADS theory assumes that trial search points must be lying on the current mesh", with helper functions project_to_mesh() supplied (p. 100);
  - the poll is the basis of the convergence analysis (pp. 16–17);
  - in PSD-MADS the pollster works on all variables with fewer directions and "ensures the convergence" (p. 97);
  - extended-poll descents run on meshes that "cannot be reduced more than the mesh of the beginning of the extended poll" (p. 88).
  - Transferable technique: when you document an extension point of your code, state the one invariant that the proof needs (here: points on the mesh) and ship the helper function that enforces it (p. 100).
- **D5 Experiments**: There is no benchmark, profile or comparison. What the guide contains:
  - **Worked example.** It has n = 5, one PB constraint, one EB constraint, 8 bounds, x0 = 0 infeasible, and a budget of 100 evaluations (p. 38, p. 43). In batch mode the log ends with best feasible f = −3.48827 and best infeasible h = 0.0114496 (p. 45). The same problem in library mode, with the same parameters as Figure 3.4 except BB_EXE (p. 66), ends at f = −3.890758281 (p. 62). The guide does not comment on the difference. Observation: the batch log prints OBJ values rounded to about 6 significant digits (1.0733100000 at BBE 3, p. 45, against 1.0733126292 in library mode, p. 62). This is consistent with the default stream precision of the `cout` in bb.cpp (p. 40), but that cause is my inference and is not stated in the guide.
  - **MATLAB smoke test.** n = 2, 134 evaluations, stopped at the minimum mesh size (p. 31). A Perl test-suite script ships for checking an installation (p. 23).
  - **Performance claims without data in the guide**:
    - defaults are "a compromise between robustness and performance obtained by developers on sets of problems", which were used for benchmarking (p. 73);
    - "Tests have suggested" that p-MADS matches the scalar version but runs faster, and that Coop-MADS "seems to give better results", with a pointer to conference slides [52] (p. 95, p. 117);
    - "tests suggested" that small bbe and ns work for PSD-MADS (bbe = 10, ns = 2) (p. 97);
    - the quadratic-model benchmarks are deferred to [35] (p. 105).
  - **Measurement infrastructure.** Counters BBE, EVAL (which includes cache hits), SIM_BBE, SGTE, BLK_EVA and TIME are available (p. 56). Budgets can be set as MAX_BB_EVAL, MAX_TIME, MAX_EVAL, MAX_SIM_BB_EVAL and MAX_SGTE_EVAL (p. 50, p. 80). SGTE_COST converts surrogate calls into blackbox-equivalents (p. 79). The seed is appended to the history, solution and stats file names by default (p. 82). DISPLAY_STATS can print rows that paste into LaTeX tables (p. 57). For bi-objective runs there are a surf (area) indicator and a Δ (largest gap between successive Pareto points) indicator (p. 90).
  - Transferable technique: count the cost in several separate units (true blackbox calls, cache hits, surrogate calls, blocks, wall-clock), give each unit its own budget, and write the seed into every output file name (pp. 50, 56, 79–82).
  - Transferable technique: for a bi-objective method, report one quality indicator (surf) and one spacing indicator (Δ), and say how a fixed budget trades one against the other: fewer, longer runs lower surf, while more, shorter runs lower Δ (p. 91).
- **D6 Literature positioning**: The guide positions NOMAD against a problem class, not against competitors. The text names no other derivative-free solver; the only comparative remark is that NOMAD "is often useful when other optimizers fail" (p. 11). Citation practice:
  - MADS [18] is cited 12 times in the text, more than any other reference. Next come the progressive barrier [20], BiMADS [28], dynamic scaling [26] and OrthoMADS [8] (my count of bracketed citations, pp. 1–112).
  - Outside the group, the guide builds on the surrogate management framework of Booker et al. [33] for static surrogates, TGP model search and the future roadmap (p. 84, p. 107, p. 111). It also cites VNS from Mladenović–Hansen [56, 46] (p. 99), TGP and treed GPs from Gramacy–Lee [43, 45], expected improvement from Jones et al. [48] (pp. 111–112), and CUTEr [42] and GAMS [34] as interfaces (p. 69).
  - By my count, 29 of the 61 bibliography entries are never cited in the text. They include the theory papers (GPS analysis [16], the tightness counterexamples [10], second order [3], the MADS erratum [14], derivative-informed GPS [6]) and most applications ([11], [39]–[41], [47], [49], [53]–[55], [57], [61]) (pp. 113–118). The bibliography therefore works as a portfolio of the method's theory and applications rather than as a support for specific claims.
  - Credit is spelled out: funders (p. 19), method designers versus code authors by version (p. 20), and the named users whose "feedbacks and tests" improved the code (p. 20).
  - The citation instruction is inconsistent: [25, 51] on p. 5 and [5, 51] on p. 47.
  - Transferable technique: in a software paper or manual, credit method designers, code authors (per version) and testers separately (p. 20).
- **D7 Writing & rhetoric**: This is manual rhetoric, organised by reader expertise: introduction, installation, getting started, how to use, tricks, advanced parameters, advanced functions (reading guide, p. 5).
  - Rules are restated in margin boxes, for example "A valid blackbox: - takes an input vector file as single argument" (p. 39) and "Batch mode parameters are provided in a file as KEYWORD argument(s)" (p. 42). "Important information is highlighted in a box" (p. 21).
  - Every parameter appears in a table with name, arguments, description and default (pp. 49–50, 79–82, 110).
  - User problems are handled with a symptom → suggestion → reference table (p. 74).
  - One small example is carried through batch mode, library mode and block-parallel mode (pp. 38–45, 62–71, 93–94).
  - Hedging is concentrated exactly where no data is shown: "tricks that may work for you" (p. 73); "Tests have suggested" and "seems to give better results" (p. 95); "So far, tests suggested" (p. 97). Statements about constraint semantics (p. 53) and theory invariants (p. 100) are categorical.
  - Formal content is minimal: one algorithm box (p. 17), two problem statements (p. 16, p. 90) and one derived bi-objective problem for sensitivity (p. 98).
  - Internal inconsistencies I found:
    - the EXTENDED_POLL_TRIGGER default is r0.1 in the table (p. 80) but "r0.2" in the text (p. 89);
    - DISPLAY_DEGREE runs over [0;3] on p. 50 but uses digits in [0;2] on p. 82;
    - the block-size parameter is called EVAL_LIST_MAX_BLOCK_SIZE on p. 84 but BB_MAX_BLOCK_SIZE on pp. 80 and 91.
  - Transferable technique: carry one tiny, fully specified example (problem, parameter file, blackbox source, full log) through every usage mode of the software. Readers can then diff behaviour across modes (pp. 38–45, 62–71, 93–94).
  - Transferable technique: in documentation, write a symptom → remedy → section table rather than a list of parameters (p. 74).
- **D8 Contributions & limits**: The contribution is at the software and dissemination level: the citable user reference for NOMAD (p. 5). The release notes tie each version to a paper or feature:
  - 3.1: bi-objective, periodic variables [24], variable groups;
  - 3.2: VNS [12];
  - 3.3: categorical variables;
  - 3.4: three parallel algorithms, LGPL licence, SCALING, sensitivity tools [23];
  - 3.5: quadratic models [35] and a random-number generator "to allow repeatability of the results on different plateforms";
  - 3.6: OrthoMADS n+1 and block evaluation;
  - 3.7.1: XMesh [26] and a single seed for all random aspects (pp. 104–107).

  The limits are stated concretely, not as boilerplate:
  - efficiency up to about 20 variables (p. 97);
  - static surrogates only (p. 84);
  - parallel runs are not repeatable, even with deterministic OrthoMADS directions (p. 95);
  - block evaluation can exceed MAX_BB_EVAL (p. 92);
  - library-mode crashes end the run (p. 59);
  - batch-mode categorical neighbours must keep the dimension (p. 88);
  - the MATLAB version lacks MPI and structure-changing categorical variables (p. 32);
  - VNS costs extra evaluations and should not be combined with BiMADS (p. 99).

  Future directions (p. 107): adaptive surrogates within the surrogate management framework, Multi-MADS for 3 or more objectives, BiMADS when feasible points are hard to find, and better handling of integer variables. For PSD-MADS: "evolved strategies" for choosing variable groups (p. 97). One gap is left unaddressed: noise is named as a defining trait (p. 11), but no mechanism for it is offered (parameter tables pp. 49–50, 79–82, 110).
  - Transferable technique: keep release notes that cite the paper behind each feature. The software history then doubles as a map of the research programme (pp. 103–107).

**Method links**:
- Method 1 (Free Search, rigid Poll): ✅ evidence. The guide gives the division of labour (pp. 16–17), the mesh invariant for any user search, with a projection helper (p. 100), and it implements VNS, LH, speculative, cache, quadratic-model and TGP searches as search-step components (pp. 58, 81, 99, 105, 111). The PSD-MADS pollster keeps convergence while the slaves work on subspaces (p. 97).
- Method 1: ⚠ variant. Structural information also enters the **Poll**, without breaking it. The default ORTHO N+1 QUAD uses a quadratic model to choose the (n+1)-th poll direction (p. 55, p. 83). Model ordering sorts poll points (p. 105). For categorical variables, the user's domain knowledge (the neighbourhood) lives in the extended poll, not in the search (pp. 87–89). The rule is therefore *the Poll may be informed, provided its theoretical properties are kept*, not *all intelligence goes into the Search*.
- Method 2 (Constraint semantics first): ✅ evidence. Here are the exact 3.7.2 wordings for EB, PB, hidden constraints and CSTR (p. 53); the c_j ≤ 0 convention and the splitting of two-sided constraints (p. 39); bounds kept out of the blackbox (p. 41); failures as a status code (p. 39); crash isolation in batch mode (p. 48); failure encoded as ∞ in the codomain (p. 16). The guide adds two mechanisms that SKILL.md does not list: PEB, which is PB until the constraint is satisfied and EB afterwards [22], and the filter F [17] (p. 53).
- Method 4 (Real blackboxes into public benchmark artifacts): ✅ evidence for step 1. The `bb.exe x.txt` contract (one input-file argument, objective then constraints on stdout, zero exit status for success) is already fixed here (p. 39, p. 40), together with interfaces to CUTEr, AMPL and GAMS (p. 69).
- Method 5 (Budget-aware benchmarking): ⚠ variant. The accounting infrastructure fully supports evaluation budgets (pp. 50, 53, 56, 64, 79–80). But the guide's own performance claims (defaults, parallel variants, PSD-MADS settings) are qualitative and are deferred to unreported benchmarks or to slides [52] (p. 73, pp. 95–97). No profile appears.
- Method 6 (The solver as research instrument): ✅ strong evidence. It shows in the defaults presented as a benchmark compromise (p. 73), the symptom table (p. 74), "Bug reports and suggestions are valuable to us!" (p. 18), the acknowledged user testers (p. 20), funders (p. 19), the release notes mapped to papers (pp. 103–107), the roadmap (p. 107) and the interfaces (p. 69).
- Method 3 (Guarantee ladder): no evidence. The guide delegates all theory (pp. 15–16).
- Research Taste #6 and Heuristic 8 (repeatability): ✅ evidence. There is a platform-independent RNG "to allow repeatability" (p. 105), one seed for all random aspects (p. 104), the seed in output file names (p. 82) and SEED DIFF for runs that are meant to differ (p. 81). The guide also bounds the claim: parallel runs are not repeatable (p. 95).
- Warning sign 5 and Heuristic 2: ✅ confirmed with pages. The preface sentence on convex, smooth-cheap and large-n problems is on p. 11. The batch-mode crash sentence is on p. 48.
- New-pattern candidate: **MADS-as-subroutine composition**. New algorithm classes are built as drivers that call the convergent base method: BiMADS (p. 90), VNS (p. 99), extended-poll descents (p. 88), Coop-MADS (p. 96), PSD-MADS (p. 97), multistart (p. 68) and sensitivity via BiMADS (p. 98).
- New-pattern candidate: **Cheap-first evaluation gating**. Constraints computable before the simulation are separated from those computed after it (p. 11). A cheap EB blackbox is run first, and the expensive one is not launched if it fails (p. 51). The current h_max is passed into eval_x so that an evaluation which is already too infeasible can be aborted and left uncounted (p. 64).
- New-pattern candidate: **The evaluation cache as shared memory and data source**. The cache prevents double evaluation, including across parallel processes (p. 96). It seeds X0 (p. 58), is kept across consecutive runs when NOMAD::Mads::reset() is used (p. 68, p. 72), feeds a cache search (p. 80) and is mined after the run for what-if analysis of constraints at zero extra cost (pp. 98–99).

**Transferable techniques**:
- Write a *do not use this method if…* sentence (convex, smooth-cheap or large-n problems) into the opening of a method paper or manual (p. 11).
- Put failure in the problem statement: f, c_j : X → ℝ ∪ {∞} (p. 16). Make the blackbox return a non-zero status on failure (p. 39). In block or parallel protocols, distinguish FAIL (never re-evaluated) from REJECT (may be resubmitted) (p. 92).
- Split every two-sided constraint into two c_j ≤ 0 outputs, and keep variable bounds out of the blackbox, in the optimizer's problem file (p. 39, p. 41).
- Chain blackboxes so that cheap unrelaxable constraints are checked first and the expensive simulation runs only when they hold (p. 51). Pass the current barrier threshold into the simulator so it can stop early and not count the call (p. 64).
- Post-optimisation sensitivity analysis in two stages. First, read the (c_j, f) pairs of the existing evaluation cache and mark the non-dominated ones, at no new cost. Then, for a constraint of interest, solve the bi-objective problem min (c_j(x), f(x)) with that constraint removed from Ω and c_j bounded (pp. 98–99).
- Put the seed into every output file name, and count surrogate calls in blackbox-equivalents (SGTE_COST) so that budgets stay comparable (p. 79, p. 82).
- Ship a single ablation switch that turns off all model-based components (DISABLE MODELS, p. 83).
