## 1. Layer 4: experiment and execution

### 1.1 He builds the test harness before, and alongside, the method

- **Benchmark interfaces come first.** In June 2002 he announced: "I just released the interface for IPOPT to CUTEr, which replaces the previous interface to the old CUTE. Dominique Orban and I have made some changes to adapt to the new release of CUTEr." (list, 2002-06, "CUTEr interface released"). In the C++ rewrite, "added CUTEr interface" is a commit of 2004-11-04, two weeks after the repository import, before the filter was split into its own file (2004-11-12). [stated + practice, primary]
- **Scalable, parametrised test problems written into the distribution.** `examples/ScalableProblems/` holds C++ versions of the Lukšan–Vlček problems and the Mittelmann PDE boundary- and distributed-control problems. The file headers read "Authors: Andreas Waechter IBM 2005-10-18/20". The README says `solve_problem PROBLEM_NAME N` solves "a problem, where PROBLEM_NAME is the name of a registered problem, and N is a positive integer determining the size of the problem". A 3-D variant was "contributed by Olaf Schenk" (commit 2007-08-02). These are the same families as the thesis's MITT test set (2002). [practice, primary]
- **Toy-scale reproductions before large runs.** His tutorial exercise says: "This is a scalable example with n ≥ 3; it will be easier to start debugging and checking the results with a small instance. The AMPL model can help to determine the correct solution for a given n, so that it is easy to verify if your code is correct." (Dagstuhl tutorial, 2009, p. 15). [stated, primary]
- **The repository's own tests are smoke tests only.** `test/run_unitTests.in` ("Author: Andreas Waechter IBM 2006-03-31") runs the example programs and fails a test only if the output lacks "EXIT: Optimal Solution Found." The repository has no regression suite on CUTEr. Performance testing lived outside it: thesis appendices B–D, per-problem tables on his homepage, and the CUTEr scripts. [practice, primary; "lived outside it" is inferred]

### 1.3 Baselines: his own code with the feature switched off, then external codes with fairness caveats

- **Ablations of his own safeguards.** RC 23149 compares "Filter (default)", "Filter (no heuristics)", "Penalty Function" and "Full Step" (backtracking disabled) inside the same code. It also includes an IPOPT run with its scaling disabled, "since the other codes do not perform any scaling of the problem statement". [practice, primary] In 2002 the thesis compared the line-search options `auglag`, `exact1`, `exact2` and others the same way (Ch. 5.1.2). [practice, primary]
- **The same move in the Northwestern prototypes.** DFO paper (*Optim. Methods Softw.* 39(4):845–873, 2024, DOI 10.1080/10556788.2024.2329588): "Alg H" versus "Alg ∅", "an algorithm that has all of the same features of Algorithm 1 except that does not utilize prior function evaluations to approximate function values at interpolation points". SOCP paper v2: "we disabled the second-order correction step (Steps 15–19) because we noticed that it was never accepted in practice." Noisy IPM (2024): the number of iterations until the termination test fires is compared with "the iteration count for a noise-less version of the instance". [practice, primary]
- **External baselines, with the conditions equalised where possible and the residual unfairness stated.** RC 23149: "Like IPOPT, KNITRO is written in Fortran and has been compiled with the same compiler and compiler options." "LOQO appears to compute the function value for each accepted iterate twice ... To correct for this, the function evaluation count for LOQO has been decreased by the number of iterations for the performance plots." The tolerance difference is admitted: "we believe that on average the chosen termination criterion for IPOPT is tighter than those for the other two codes". [practice, primary]
- **A caveat that favours the baseline.** Tu, Wächter & Wei, *IEEE Trans. Power Syst.* 36(1):303–312, 2021, DOI 10.1109/TPWRS.2020.3002189 (arXiv:2002.08003 v2): "the decomposition algorithm was given a flat start as starting point, which is less favorable than the starting point included in the MATPOWER models that was used by the MATPOWER optimization algorithm." [practice, primary]
- **A tuning budget for the rival baseline.** Peña-Ordieres, Luedtke & Wächter (*SIAM J. Optim.* 30(3), 2020; arXiv:1905.07377 v2): "In order to obtain comparable solutions between the MIP and the NLP formulations, we tuned the risk level α of the MIP formulation to ensure that the solutions obtained were all feasible. This is similar to tuning the ε parameter in the NLP formulation." [practice, primary]
- **The monolithic solve as the natural baseline for decomposition.** Lou, Luo, Wächter & Wei, *SIAM J. Optim.* 36(3):1211–1238, 2026, DOI 10.1137/25M1728661 (arXiv:2501.11700 v3): the decomposition is compared against "Ipopt to solve the undecomposed monolithic instances". The paper reports where the baseline wins: "As expected, for small instances, Ipopt is much faster". [practice, primary]

### 1.4 Timing protocol: controlled measurement, or no timing at all

- 2002 thesis: "Since we observed inconsistencies in those CPU times when multiple applications were running, it was ensured that the solver executable was the only active program. Despite this precaution we still observed deviations in some cases of up to 15% and therefore recommend to use the reported CPU times with caution." AMPL `.nl` files were generated once, so AMPL time is excluded. [practice + stated, primary]
- 2004 preprint: "Since the CPU time is measured in 0.01s increments on the machine used for obtaining the results, we excluded the 444 test problems from the graph, for which the CPU time for the fastest solver was less than 0.05s". [practice, primary]
- 2020 AC-OPF v2: "We had exclusive access to this machine so that the time measurements are not affected by other processes. For all experiments we report the wall clock time averaged over three runs with identical data in order to reduce the effect of random variations in run times. Setup time, such as reading and generating data, is not included." [practice, primary]
- 2022/2023 SOCP prototype (MATLAB + CPLEX): the timing comparison is declined, with a reason. The Matlab CPLEX interface does not allow callbacks for adding or removing hyperplanes, "Consequently, we do not report solution times here." (v2; v1 says "As a result"). [practice, primary]

### 1.7 How a heuristic lives and dies: observe → option → test → default → maybe removal

The repository shows the whole cycle several times [practice, primary unless marked]:

1. **Birth from an observed failure**, stated as such. RC 23149 §3.2: "We also noticed that in some cases the full step ... is rejected in successive iterations"; §3.9: "In a few instances we observed that the search directions ... become very small compared to the size of the iterate". Commits: "added option expect_infeasible_problem as heuristic to switch to restoration phase early and longer in order to detect an infeasible problem early on" (2005-03-25); "added heuristic to return error message when algorithm seems to cycle ("acceptable level")" (2005-05-04); "added heuristic to ignore wrong inertia in some cases" (2007-09-29).
2. **Exposure as an option before it becomes a default.** RC 23149 on equilibration scaling (MC19/MC29): "While these strategies seem to work well in some instances, the overall performance on the considered test set became worse. Nevertheless, these procedures are available to users of our implementation as options." The default is described as "rather conservative".
3. **Defaults changed on test evidence, with the reason recorded.** "changed default for scaling_method to none (something is wrong with MC19 scaling at the moment)" (2005-05-21). On keeping MC19 off by default: "I didn't do this, because in my tests, it wasn't leading to considerable more robust results, but using MC19 makes the computation quite a bit slower..." (list, 2006-04-10, "MA27 error message"). Other default changes: "changed default for alpha_for_y back to primal" (2007-07-13) and "change alpha back to 1e-2" (2007-10-05).
4. **Removal when it hurts, left in the code as a note.** `IpIpoptData.cpp`, `#if 0` block (git blame: Wächter, 2009-10-29): "I (AW) took the following heuristic out again, since it seemed that the restoration phase tolerance became too tight by default. I originally probably put it in to avoid that a claim of infeasibility is made prematurely... let's see if someone starts screaming..." Same day, commit: "changed resto.tol default to that of tol instead of 1e-2*tol - the latter seemed to strict". ChangeLog 3.8.0: "changed default convergence tolerance in restoration phase (now same as regular tolerance)".
5. **Replacement of a special-case update.** Commits 2010-11-17 "added option to use usual initialization of Hessian approximation in restoration phase" and 2010-11-22 "made new Hessian approximation default"; ChangeLog 3.9.1 "improved Hessian update for restoration phase". The current option text reads: "Until Nov 2010, Ipopt used a special update during the restoration phase, but it turned out that this does not work well." Blame puts that wording on a 2019 edit by Vigerske, so the sentence is **not** attributable to Wächter. The change itself is his. [practice, primary]
6. **Candour in the release notes.** ChangeLog 3.4.2 (2008-07-18; the pickaxe attributes the line to Wächter): "penalty function version does no longer crash if it wants to go to restoration phase (not that this really helps convergence though)". [stated, primary]

The restoration phase itself grew by accretion in 2004–2005 commits: "added restoration phase for the restoration phase" (2005-02-11); "added "soft" restoration phase" (2005-04-29); "store the most recent iteration with acceptable optimality error, and restore in case of failure" (2005-05-05); "BUGFIX: soft restoration phase crashed if tiny step was encountered" (2005-05-10). Later fixes answered outside reports: "fix for bug reported by Nick Sahinidis: In case of catastrophic failure in restoration phase, no iterate might be available to be returned to the user. This is to avoid seg fault" (2012-11-06). [practice, primary]

### 1.9 Prototypes at Northwestern reuse the Ipopt craft

[practice, primary] The noisy constrained IPM (arXiv:2502.11302) projects the starting point "using the strategy proposed in Section 3.6 of [31]" (the IPOPT paper). It scales functions whose initial gradient ℓ∞-norm exceeds 10, "as is typical for software for solving continuous optimization problems". It does "a block LDL factorization ... then checking its inertia", adding "sequentially larger multiples of the identity matrix". The SOCP prototype relaxes the Armijo test "to account for cancellation error" (the same device as the Ipopt paper) and falls back to other QP algorithms when CPLEX fails (v1 §5.1; v2 §5.1). The two-stage framework calls Ipopt's internal linear algebra: "Due to the object-oriented design of Ipopt, one can easily access the internal linear algebra routines in Ipopt and use them to efficiently solve (2.7) and similar systems." (arXiv:2501.11700 v3 §7.1). The SC-AC-OPF competition code notes: "it is important to evaluate the objective value explicitly, rather than consider the objective value reported by Ipopt, since the latter is influenced by internal relaxations of the bound constraints" (Curtis, Molzahn, Tu, Wächter, Wei, Wong, arXiv:2110.01737 v1; *Oper. Res.* 2023).
Era note: these are small-team prototypes (MATLAB R2020b/R2021b, Python/SciPy, a student's C++ thesis code), not production code. Students first-author them.

## 2. Layer 5: judging results

- **He reports the evidence that weakens his case.** RC 23149: "Full Step" solved 86.1%, which "might indicate that in many cases Newton's method does not require a safeguarding scheme ... or alternatively, that many problems in the test set are not very difficult" (quoted in 01). "KNITRO seems to require overall less function evaluations than IPOPT for the given test set." [practice, primary]
- **He disclaims competitive benchmarking.** The thesis in 2002 says of its comparison that it is "intended to demonstrate Ipopt's potential as a general purpose NLP solver, not as a thorough comparison of the three discussed methods, which is beyond the scope of this dissertation. Such a direct comparison should be performed by an independent party and would have to ensure that the conditions for each method (such as convergence criteria) are as similar as possible." He repeats the disclaimer in 2004: "not meant to be a rigorous assessment" (quoted in 01). [stated, primary; repeated in 2002 and 2004]
- **Local solutions are handled explicitly.** Thesis eq. (5.3) discards problems whose final objectives differ by more than 10^-3 (relative), and the thesis calls it "of course only a simple heuristic". RC 23149: "75 problems were excluded because the final objective function values were too different." 2026 two-stage paper: "Despite the nonconvexity of the problem, the final objective values of Ipopt and our algorithm are identical." [practice, primary]
- **Failures are explained against the theorem's assumptions, not hidden.** Thesis 2002: "When facing a relatively high failure rate of 11% we should keep in mind that the CUTE test set is a fairly colorful selection of problems, and that there are a number of problems that do not satisfy the assumptions made in Chapter 4". SOCP v2: CBLIB subsets "clay*, fo[7-9]*, m[3-9]*, no7*, o[7-9]*" "are degenerate ... and the assumption necessary to prove fast local convergence is violated. This matches the observations in the table". Two-stage v3, Appendix A: "Chapter 4.7.3 in [25] presents an instance with linear subproblems in which the method converges to a spurious solution that is not a local minimizer." [practice, primary]
- **A result on the claim itself, not a performance race.** SOCP v2: "We emphasize that the purpose of our implementation is to assess whether the proposed algorithm exhibits behavior that validates the stated goals: Convergence from any starting point and rapid local convergence to highly accurate solutions." Noisy IPM 2024: "we present numerical results that show that the theoretical findings in Sections 3 and 4 can be observed in practice." Noisy IPM 2025: "The purpose of our numerical experiments is to demonstrate the practical performance of our proposed algorithm on a large and diverse set of test problems." [stated, primary]
- **Conservative tests are flagged.** Noisy IPM 2024: "Since the derivation of the termination test relies on some conservative inequalities, we cannot expect that it can predict the smallest achievable [measure] accurately, so in a practical setting, one may want to run the algorithm a few additional iterations after the test has been triggered." ("[measure]" replaces a formula lost in extraction.) In 2025 the termination tests were disabled on purpose, "in order to be confident that the algorithm has reached the highest quality solution that it can in each run." [practice, primary]
- **Theory and heuristic are labelled apart in what he tells users.** "There is no theory ensuring convergence for the quasi-Newton option (while there is for the default version), and it is mainly thought to be a heuristic for the case there second derivatives are not available. It works in many cases (in fact, we use it every day to optimize computer chips), but there are limits, and you might just have found such as case ;-)" (list, 2008-01-08, "limited-memory quasi-Newton approximation"). Also: "(but, as I guess we all know, theory and practice can sometimes differ widely... :)" (list, 2007-03-13). The option text says of `line_search_method`: "Only the "filter" choice is officially supported. But sometimes, good results might be obtained with the other choices." (`IpAlgBuilder.cpp`; wording not blamed). [stated, primary]
- **He admits when a default has no justification.** "Well, the minimal values are somewhat arbitrary. I don't have good arguments for one or the other. ... I guess this was more or less what went through my mind when I did this." (list, 2009-07-08, "Adaptive mu update / degenerate problems"). [stated, primary]

## 3. How he answers criticism, bug reports and user failure reports (mailing list, 2002–2012)

Corpus: 681 posts by him among 4,824 archived messages. Rough regex counts on his own text (quoted lines removed; a post can match several patterns): linear-solver names in 17% of posts, Hessian or second derivatives 14%, bug/fix 13%, "I don't know" / "not sure" / "no idea" 11% (73 posts), "you might want to / I would suggest" 12%, scaling 9%, starting point 8%, derivative checker 4%, inviting a code contribution 5%, asking for the model or code 5%. - **He reproduces the problem first.** He ran a published AMPL model himself (the Goddard rocket model from Vanderbei's collection): "If I just use Ipopt's default options, the problem is solved well ... However, if I specify the option to use the limit-memory BFGS approximation, Ipopt doesn't converge; it can't find a feasible point." (2008-01-08). (2008-11-18). "Do you have an AMPL model that you can email me to reproduce the exception?" (2010-02-26). [practice, primary]
- **His diagnostic order**, reconstructed from the posts [inferred from repeated practice, primary sources]:
  1. Derivatives. "If you modeled your problem in C or C++ (and not in AMPL or GAMS), you definitely should run the derivative checker to make sure you didn't make a mistake assembling the first derivatives (it is so easy to have a typo here... :-) )" (2008-01-08).
  2. Memory errors in user code. "If there is indeed a bug in Ipopt (which is possible, but most of time issues like this are due to bugs in user code) this would also show us exactly where." (2010-06-23, after recommending valgrind).
  3. Scaling of gradients, not of values. "Ideally, the "typical" values in the Jabocian should be on the order of 1 to 10." (2005-11-09); "(The VALUE of the function does not matter that much)" (2007-05-03); on MC19 automatic scaling: "But that is a heuristic that often doesn't do a good job. Since you probably have a good idea how the scaling should be, I recommend that you scale your problem formulation directly." (2005-09-25).
  4. Starting point and local minima. "given that this is probably a problem with multiple local minima, the choice of the starting point might make a big difference in terms of which local solution Ipopt converges to" (2011-02-25).
  5. Constraint qualifications and degeneracy. On "Restoration Phase Failed": "One of the assumptions is that the gradients of the active constraints are linearly independent, and this is a condition that could be violated in practice." and "Other than that, the restoration phase can also fail if the problem is really nasty, if derivatives are incorrect, the problem is badly scaled..." (2007-05-15).
  6. Linear solver, BLAS and floating point. "In principle, the Ipopt code is deterministic, and results should be 100% reproducible." ... "In general, for difficult problems, I have often observed a different number of iterations (or sometimes success vs. failure) when compiling the code with different compiler options, or when changing the operating system" (2010-02-26).

## 5. Failures, abandoned directions and parked code (process-level; see 01 §3 for the publication-level list)

1. **Linearly-dependent-constraint detection** (`dependency_detector`, commit 2007-04-19 "added support for dependent constraint detection"). He wrote in 2009: "(Some time ago, I added some code that would try to identify at the very beginning the constraints that are redundant, and they would be removed from the problem statement that Ipopt sees, but this did not work very well, so I didn't follow up on this ... This is the unsupported, undocumented dependency_detector option. It's in the code, so you could try it if you want, but I won't be able to help with that :-) )." And in 2010: "Well, at some point we tried to get this information from the linear solvers and potentially use it as preprocessing, but it didn't work very well, so we don't use or advertize it." He quoted the option text "This is experimental and does not work well." He dropped the direction but left the code in the solver. [stated + practice, primary]
2. **Golden-section search in log space for the barrier centering parameter.** "even worse than search in unscaled space"; commented out (source comment). [practice, primary]
3. **Equilibration scaling (MC19/MC29) as the default.** It made overall performance worse on CUTEr (RC 23149) and "something is wrong with MC19 scaling at the moment" (2005). It survives as an option. [practice, primary]
4. **The restoration-phase tolerance heuristic (resto.tol = 10^-2·tol)**, removed in 2009 ("let's see if someone starts screaming"). **The special L-BFGS update in restoration**, replaced in Nov 2010. [practice, primary]
5. **The penalty-function line search** was kept only as a comparison option: "not guaranteed to converge", and a crash fix "(not that this really helps convergence though)". [stated, primary]
6. **The distributed-memory / PETSc line** (`parallel` branch: ParAmplNlp, WSMP-parallel "ParCollect", a libMesh/PETSc PDE example, "experiments with AMR", 2009–2011). `git merge-base --is-ancestor origin/parallel stable/3.14` reports it **not merged**, and its last commit is 2013-04-24. ChangeLog 3.7.1: "first code for iterative WSMP version (experimental and undocumented)". Whether the branch was abandoned or superseded is **not documented**. [practice, primary; "abandoned" inferred]
7. **Complementarity constraints in the C++ code**: "Sorry, there are no plans to include complementarity constraints into the C++ version at this point." He suggested a penalty reformulation instead (list, 2006-02). [stated, primary]
8. **Full-space or reduced-space BFGS in the C++ code**: "at this point there are no plans to implement a full-space or reduced-space regular BFGS method" (2006-10-05). The reduced-space machinery of the thesis was not carried over (see 01 §3.3). [stated, primary]
9. **The Fortran code**: "Sorry, no. The Fortran version is no longer maintained." (2009-09). [stated, primary]
10. **Inexact function values: a limit he stated, later taken up as research.** 2009: "In principle, it is probably possible to design an optimization algorithm that is able to work with approximate values of the function and derivative values and might tell your simulator, who accurate the computation has to be. But Ipopt is not such an algorithm." His suggested workaround "would just be a heuristic, would require a lot of tuning, and will not always work." (list, 2009-05-11, "adaptive error tolerance for integrator"). Fifteen years later come the noisy-IPM papers (Dezfulian & Wächter 2024/2026; Curtis, Dezfulian & Waechter 2025). Linking the 2009 post to the 2024 papers is **inferred**. [stated, primary]
11. **No errata or retractions**: a Crossref query (author "Wächter" plus erratum/corrigendum/correction) returned only namesakes. [practice, secondary]

## Contradictions (kept, not reconciled)

1. **Filter versus "simple line search (without filter)".** His signature globalization is the filter line search: the thesis, SIOPT 2005 and IPOPT 2006, plus the current Ipopt option text that only "filter" is "officially supported". The Gurobi 13.0 NL barrier he presented lists "Simple line search (without filter)" among its improvements. Yet in 2009 he wrote on the list that the filter "can actually be more restricting". His reasons at Gurobi are **not known**.
2. **"The purpose of the interior point approach is not to make decisions about activities" (2006) versus his later active-set turn.** Hot-started active-set QP (SIOPT 2015) and the warm-startable SOCP SQP (2024) were built because IPMs are "Difficult to warm-start" (CNLS 2020). Both statements are about different jobs, but they pull in opposite directions.
3. **Heuristics: removed versus retained.** He removes heuristics that hurt defaults (resto.tol 2009, restoration L-BFGS 2010). He keeps ones he calls ineffective as selectable options (dependency detector: "does not work well"; penalty line search: "not that this really helps convergence"; MC19 scaling). Retention is not tied to evidence of usefulness.
4. **Exact values required versus noisy algorithms.** 2009: "Ipopt is not such an algorithm", with approximate function values "would just be a heuristic". 2024–2026: convergence theory for IPMs with noisy function and derivative values. This may be development over time rather than a contradiction [inferred].
5. **Where the C++ rewrite started.** Source headers read "Carl Laird, Andreas Waechter IBM 2004-08-13" (118 files) and "2004-03-17" (some linear-solver files). The git history starts 2004-10-21, and 3.0.0 is "First official release of the new C++ implementation" (2005-08-26). This supports the Ipopt docs' 2004–2005 dating over the homepage's "2005-2006" (01, Contradiction 1).
6. **Luo & Wächter v1 vs v2 numbers.** Solve counts, tolerances (10^-10 vs 10^-9) and the error-reduction claim (3–4 vs 4 orders) differ between versions. The MOSEK setting was changed, so the numbers are not comparable.
7. **The adaptive-barrier preprint's author list.** Optimization Online 2005/03/1089 lists "Jorge Nocedal, Richard A. Waltz" (IBM report RC23563). The published SIOPT 2009 paper has Nocedal, Wächter, Waltz. Crossref gives 20(3) **2010** for Curtis–Nocedal–Wächter (01 gives 2009, the online year).
8. **Who wrote the current caveat texts.** "does not work well" in the L-BFGS restoration option is blamed to Vigerske (2019). The "experimental and does not work well" dependency-detector text is blamed to Vigerske (2021), yet Wächter quoted the same wording on the list in 2010. Blame shows the last edit, not the origin.
